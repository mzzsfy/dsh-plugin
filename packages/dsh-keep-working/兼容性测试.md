# dsh-keep-working 兼容性测试

## 测试分层与执行流程

- L1 单元:`node --test "test/*.test.mjs"`,4 个文件 64 条,全部为纯函数或假 host 驱动,毫秒级
- L2 契约:包根 `node scripts/smoke-load.mjs` 全包加载,验证命名导出与模块解析
- L3 功能面:隔离宿主 boot,验证提示词注入、实时恢复、重启扫描、卸载撤销
- L4 共存层:与 profile 全家桶共启,确认不干扰其它插件的回合观察

L3 / L4 的隔离方法见仓库根 `docs/兼容性测试/测试与隔离方法.md`;AI 会话执行时按 `AGENTS.md` 的「AI 自测规约」,只用 `.compat/` 下的隔离宿主,不碰生产 `~/.dsh` 与 3080 实例。

## L2 判据

`node scripts/smoke-load.mjs` 输出 `OK @mzzsfy/dsh-keep-working`;任一命名导出缺失或不存在的依赖都会当场失败。

## L3 功能面断言

### 一、提示词注入面

- 主会话首轮 system prompt 含结案规则两行
- 插件卸载后,新回合的 system prompt 不再含该段落

### 二、结案判定面

- 回合写文件但未 `present` → 收到一条结案提醒
- 回合末行 `(TASK_DONE)` 且未写文件 → 不发送
- `present` 之后又改文件 → 视为未结案并提醒
- 末行 `(TASK_BLOCKED: 原因)` → 不发送

### 三、恢复面

- `error` 可重试 → 收到带错误码的继续消息
- 永久错误(401 / 余额 / 模型不存在)→ 不发送
- `max-tokens` / `interrupted` → 收到对应文案
- 用户点停止(`abort cause = user`)→ 不发送
- 子会话、维护轮 → 不发送

### 四、节奏面

- `graceMs` 内开启新回合 → 待发送被取消
- 连续 `maxConsecutive` 次后 → 不再发送
- 断网 → 挂起;恢复网络 → 补发一次

### 五、重启恢复面

- 未结案会话 → 冷启动后被拉起并收到恢复消息
- 已结案、用户取消、已归档、超 `freshMs` 会话 → 不拉起
- `active` 且 `disarmed` 的 goal → 重新武装

### 六、卸载撤销面

- 卸载后不再消费 `session/event`,无残留定时器
- 提示词段落随 fiber 销毁移除

## L4 共存层

与 profile 全家桶共启:确认其它插件(通知、用量、会话管理)仍能正常观察回合;本包的 followup 消息不会被误判为人工输入。

### 端到端实测(隔离宿主 + echo 上游)

工位:`run.mjs --keep` 驻留宿主 + echo 模拟器;经 `session/create`、`session/prompt` 真实驱动,以 `llm-echo.jsonl` 请求体与会话存储为证据。每个场景独立会话,提示词带 `[Sx]` 标记定位归属,场景结束取消会话。

| 场景 | 注入 | 预期 | 实测 |
|---|---|---|---|
| S1 有写入 + present | 同条回复发起 write 与 present | 不提醒 | 不提醒 |
| S2 有写入 + 无 present | write 后接纯文本 | 提醒 | 提醒,文件真实落盘 |
| S3 无写入 + `(TASK_DONE)` | 末行标记 | 不提醒 | 不提醒 |
| S4 无写入 + `(TASK_BLOCKED)` | 末行标记 | 不提醒 | 不提醒 |
| S5 无写入 + 无标记 | 纯文本 | 提醒 | 提醒 |
| S6 present 后再写文件 | 三步序列 | 提醒 | 不可稳定构造,见下 |
| S7 临时错误 500 | HTTP 500 | 提醒 | 提醒 |
| S8 永久错误 401 | HTTP 401 | 不提醒 | 不提醒(修复后) |
| S9 无可见输出 | 空文本 + 仅 thinking | 提醒 | 提醒 |

**实测发现并修复的缺陷**:S8 首轮出现误提醒。宿主把 HTTP 状态并进 `turn/end` 的 `error.message`(`401 {"error":...}`),没有独立 `status` 字段,分类器只认数字字段,401 因此被当临时错误重试。已补两条判据:文本中的 `401` / `403` 视为永久,`\bauth\b` 独立词视为永久。

**S6 为何不可构造**:present 之后宿主仍会发起一轮请求(标题生成等旁路),它按 echo 的 FIFO 抢走剧本下一条,导致“present 后写文件”排不进执行序列;把 write 与 present 收进同一条回复时,宿主又在 present 处收束该回合。该规则由 `test/closure.test.mjs` S3 与 `test/engine.test.mjs` S17 覆盖。

**测试自身修正**:首轮矩阵按单一文案判定提醒,漏掉 silent 场景;已改为匹配全部提醒文案。场景之间加了 12 秒静默 + 队列清空,避免上一会话的续轮抢走剧本。

**生产实测(提示词歧义)**:上线后第一轮,模型在 present 之后又补了一行 `(TASK_DONE)`。判定层在 present 有效时已短路结案,标记不参与判定,所以不算漏拦;问题在旧提示词只写了“不要用 (TASK_DONE) 代替 present”,没禁止“交付完再补标记”。已改成二选一表述:有文件产出只 present,不写标记;无文件产出才写标记。判定层不追罚冗余标记,避免为一行文字多烧一轮。

### 重启恢复的两个缺陷

对照参考实现排查出两处:

1. **扫描只跑一次**。宿主刚启动时 `sessionQuery.listSessions()` 可能还是空,原实现拿到空数组就永久放弃,重启恢复静默失效。改为每 3 秒重试,直到列出会话或超出 `freshMs` 窗口。
2. **恢复缺 preset 挂载**。`agents.resume` 不带 preset 时 agent 没有工具与提示变量,恢复后发出的请求无路由。现在按 `header.agentPreset` 走 `agentPresets.resolve` + `mount`。

**工位说明**:`scripts/compat/boot-keep.mjs` 默认每轮清 `home/sessions`,跨重启验证要加 `--keep-sessions`。加该参数后已实测通过:

```
列出 4 个存储会话
会话 session-8b1e4f46 事件 37 判定 resume
已恢复 session-8b1e4f46
...
```

echo 端 26 个请求里 22 个携带重启恢复文案,证明确实重新发起了 LLM 请求。

**第三个缺陷(端到端才暴露)**:扫描里直接访问 `ctx.workspaceRegistry` 抛 `cannot get property "workspaceRegistry" without inject`,整轮扫描中断,上层 catch 后每 3 秒重试,永远走不到判定。改成 `ctx.get('workspaceRegistry')` 并加 try/catch 兜底(归档快照未就绪按空集处理,fail-open)。

### 设置面板

宿主 0.2.2-rc.1 已移除 `settings.register`,`describe()/update()` 才是现役接口,表单来自插件 cordis Config 的 volatile 字段。实测:

- `GET /api/keep-working/config` 返回 `{ok:true, value, defaults}`
- `POST` 写入 `graceMs: 6000` 后回读为 6000,并触发运行期重建
- 客户端半区在 `settings.section` 注册「持续工作」分区,`inject: ['slots']` 缺失时宿主报 `cannot get property "slots" without inject`,已补

### 扫描吞吐

首版逐条 `observeSession` 解码全量事件,生产 3615 个会话要跑半小时。两级削减:

1. **先筛后读**。宿主的 `persistence.list()` 要为每个会话解析快照,3615 个耗时 8.6 秒。改为直接扫 `$DSH_HOME/sessions` 目录取 id 与 mtime(1918 个文件 210ms),只对命中者调 `persistence.stat()` 取头部。`持久层快照` 与 `目录扫出` 两条日志区分走了哪条路。
2. **只判尾部**。回合正常结束且有可见回复就跳过,不解析整轮 present。

工位实测:

```
扫描开始        10:17:53.064
目录扫出 1 个近期会话   10:17:53.065
按修改时间筛出 1 个候选  10:17:53.072
已恢复           10:17:53.163
```

从扫描开始到恢复完成 **100ms**,两个会话时 316ms。生产同款数据筛出 4 个候选、恢复 3 个共 17.5 秒,其中 8.6 秒是改前的 `persistence.list()` 固定开销。

### 归档集合的方向性

恢复是写操作,误恢复已归档会话会真的发请求消耗额度。生产实测踩到过:冷启动 25 秒时 `workspaceRegistry` 还在异步加载,`archivedSessionIds` 抛 `workspace registry is not started yet`,旧代码 catch 后当空集处理,导致 3 个恢复里有 2 个是已归档会话。

现在改为拿不到权威集合就本轮不恢复、下一轮重试(`result.complete = false`),方向与只读场景的 fail-open 相反。
