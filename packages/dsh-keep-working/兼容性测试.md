# dsh-keep-working 兼容性测试

## 测试分层与执行流程

- L1 单元:`node --test "test/*.test.mjs"`,16 个文件 255 条,全部为纯函数或假 host 驱动,毫秒级
- L2 契约:包根 `node scripts/smoke-load.mjs` 全包加载,验证命名导出与模块解析
- L3 功能面:隔离宿主 boot,验证提示词注入、实时恢复、重启扫描、卸载撤销
- L4 共存层:与 profile 全家桶共启,确认不干扰其它插件的回合观察

L3 / L4 的隔离方法见仓库根 `docs/兼容性测试/测试与隔离方法.md`;AI 会话执行时按 `AGENTS.md` 的「AI 自测规约」,只用 `.compat/` 下的隔离宿主,不碰生产 `~/.dsh` 与 3080 实例。

## L3 功能面断言

### 一、提示词注入面

- 主会话首轮 system prompt 含结案规则
- 插件卸载后,新回合的 system prompt 不再含该段落

### 二、结案判定面

- 回合写文件但未 `present` → 实时收到结案提醒
- 写入 + 末行 `TASK_DONE` + 无可见回答 → 重启扫描仍要 present
- 写入但末条有可见回答 → 重启扫描不恢复
- 前面交代过、末步只剩思考或工具调用 → 视为没交代:实时按空回合/结案提醒恢复,重启扫描同样恢复
- 回合末行裸 `TASK_DONE` 且未写文件 → 不发送
- 带括号、下划线、连字符、反引号或粗体的标记 → 不认,按未结案处理
- 回合中途真人插话、模型随后未结案就结束 → 仍补提醒(插话不是结案凭据)
- 实时 `interrupted` / 重启取消 → 始终补中断提醒,不看标记
- 重启扫描:未闭合 / `interrupted` / 重启取消的回合,末行已结案 → 仍恢复中断
- 本回合最近 10 条消息里有 `present` → 重启扫描不恢复
- `present` 超出最近 10 条消息 → 仍恢复
- 上一回合的 done 不当作新回合的结案
- `present` 之后又改文件 → 实时视为未结案并提醒;扫描末条有文本时仍跳过
- 实时 `error` / `max-tokens` 但已 `present` → 不发送
- 末行 `TASK_BLOCKED: 原因` → 不发送
- 有排队消息的唤醒消息 → 文案只有「继续」;用户主动取消除外

### 三、恢复面

- `error` 可重试 → 收到带错误码的继续消息
- 默认所有 `error` 都重试;开启「区分永久错误」时仅请求结构错误(上下文超限 / 参数非法 / 缺适配器)不发送,401、余额、模型不存在等上游级错误仍重试
- `max-tokens` / `interrupted` → 收到对应文案
- `blocked`(宿主 pre-step 被拒)→ 按中断文案补发;末行已结案、会话已归档、子会话不发送
- 目标接回:冷却期内或接回抛错 → 回落补中断消息;冷却过后再次接回
- 目标被预检拒绝记成 `blocked(prompt-rejected)` → 交回 goal driver,不补消息;其他阻塞码不接管
- 用户点停止(`abort cause = user`)→ 不发送
- 子会话 → 不发送

### 三之二、排队输入面(实时)

宿主的失败回合不消费 durable inbox:回合抛出后不再进下一回合,`next-turn` / `next-step` 里的输入停在队列里,agent 回 idle。实时判定必须自己重放 `agent/inbox/spliced` 把队列跑掉。

- `error` 回合且 `next-turn` 有排队输入 → 插队(`steer`)收到「继续」,不是错误文案;新回合先消费排队输入
- `next-step` 的真人插话同样算排队输入;只有运行时上下文注入时不算,仍按原因文案 `followup`
- `interrupted` / `max-tokens` / `blocked` 同上:有排队输入就只发「继续」
- 连续上限已满(`maxConsecutive` 用尽)后出现排队输入 → 仍插队唤醒;队列每唤醒一次消费一条,不构成无限重试
- `completed` 且已结案 + 排队输入 → 实时不补消息(宿主自己开下一回合),不得出现重复回合
- 用户主动取消 + 排队输入 → 不发送
- 排队唤醒的文案固定为「继续」,与 `continueText` / `restartText` 配置无关
- 开启「区分永久错误」后被判永久的请求结构错误,只要队列有输入仍唤醒一次;每次唤醒消费一条,队列耗尽后回到永久错误口径

### 四、节奏面

- `graceMs` 内开启新回合 → 待发送被取消
- 离线探测在途时开启新回合 → 探测返回后不补发
- 连续 `maxConsecutive` 次后 → 不再发送
- 断网 → 挂起;恢复网络 → 补发一次

### 五、重启恢复面

- 未结案会话 → 冷启动后被拉起并收到恢复消息
- 前面交代过但末步只剩思考的会话 → 冷启动后被拉起(末条文本口径)
- 已结案、用户取消、已归档、超 `freshMs` 会话 → 不拉起
- 会话已被客户端打开(崩溃重启后浏览器重连即物化,agent 空闲)→ 仍补恢复消息,且不再重复 `resume`
- 会话正在跑回合(`agent.status === 'running'`)→ 不判定、不补消息
- 尾部正常结束但 durable inbox 有排队消息 → 被拉起;补发消息走 `steer` 插队,`next-turn` 队列顺序不变
- `next-step` 的运行时上下文不算排队消息;真人插话才算
- 重启恢复文案独立于实时中断文案:改 `restartText` 不影响 `continueTextInterrupted`,截断 / 空回合仍走专项文案
- 有排队消息但最后回合是用户主动取消 → 不拉起
- `active` 且 `disarmed` 的 goal → 重新武装
- 尾部 `blocked`(维护闸门拒绝 pre-step)→ 冷启动按中断拉起
- `blocked(prompt-rejected)` 的 goal → 重新武装交回 driver,不补消息;其他阻塞码不接管

### 六、卸载撤销面

- 卸载后不再消费 `session/event`,无残留定时器
- 卸载时在途扫描立即失效:观察返回后不再 `resume` / `followup`,也不再排重试
- 设置重建时旧代 seen 登记全部撤销;观察在途由新代重扫,resume 已物化的 agent 由新代补投恢复消息
- 提示词段落随 fiber 销毁移除

## L4 共存层

与 profile 全家桶共启:确认其它插件(通知、用量、会话管理)仍能正常观察回合;本包的 followup 消息不会被误判为人工输入。

### 端到端实测(隔离宿主 + echo 上游)

工位:`run.mjs --keep` 驻留宿主 + echo 模拟器;经 `session/create`、`session/prompt` 真实驱动,以 `llm-echo.jsonl` 请求体与会话存储为证据。每个场景独立会话,提示词带 `[Sx]` 标记定位归属,场景结束取消会话。

| 场景 | 注入 | 预期 | 实测 |
|---|---|---|---|
| S1 写入 + present | 同条回复发起 write 与 present | 不提醒 | 不提醒 |
| S2 写入 + 无 present | write 后接纯文本 | 提醒 | 提醒,文件真实落盘 |
| S3 无写入 + `(TASK_DONE)` | 末行标记 | 不提醒 | 不提醒 |
| S4 无写入 + `(TASK_BLOCKED)` | 末行标记 | 不提醒 | 不提醒 |
| S5 无写入 + 无标记 | 纯文本 | 提醒 | 提醒 |
| S6 present 后再写文件 | 三步序列 | 提醒 | 不可稳定构造,见下 |
| S7 临时错误 500 | HTTP 500 | 提醒 | 提醒 |
| S8 永久错误 401 | HTTP 401 | 不提醒(旧判据;现改为按上游级重试) | 不提醒(当时) |
| S9 无可见输出 | 空文本 + 仅 thinking | 提醒 | 提醒 |

注:上表是标记改版前的历史实测。当前规范为裸 `TASK_DONE` / `TASK_BLOCKED: 原因` 严格匹配,任何文件写入都要求 present;重启扫描正常结束时末条 assistant 有可见文本即跳过,末条无文本才看 done / 最近 10 条 present,中断类不看结案,有排队消息优先恢复。L1 已覆盖,L3 未重跑,旧括号标记不再结案。

**实测发现并修复的缺陷**:S8 首轮出现误提醒。宿主把 HTTP 状态并进 `turn/end` 的 `error.message`(`401 {"error":...}`),没有独立 `status` 字段,分类器只认数字字段,401 因此被当临时错误重试。当时补了「文本 401/403 视为永久」;现行策略已改为默认全部重试,`401/403` 与鉴权、余额、模型不存在等上游级错误一律按临时处理(中转后面可能还有别的上游),仅上下文超限、参数非法等请求结构错误可由「区分永久错误」开关跳过。

**S6 为何不可构造**:present 之后宿主仍会发起一轮请求(标题生成等旁路),它按 echo 的 FIFO 抢走剧本下一条,导致“present 后写文件”排不进执行序列;把 write 与 present 收进同一条回复时,宿主又在 present 处收束该回合。该规则由 `test/closure.test.mjs` S3 与 `test/engine.test.mjs` S17 覆盖。

**测试自身修正**:首轮矩阵按单一文案判定提醒,漏掉 silent 场景;已改为匹配全部提醒文案。场景之间加了 12 秒静默 + 队列清空,避免上一会话的续轮抢走剧本。

**生产实测(提示词歧义)**:上线后第一轮,模型在 present 之后又补了一行 `(TASK_DONE)`。判定层在 present 有效时已短路结案,标记不参与判定,所以不算漏拦;问题在旧提示词只写了“不要用 (TASK_DONE) 代替 present”,没禁止“交付完再补标记”。已改成二选一表述:有文件产出只 present,不写标记;无文件产出才写标记。判定层不追罚冗余标记,避免为一行文字多烧一轮。

### 重启恢复的两个缺陷

对照参考实现排查出两处:

1. **扫描只跑一次**。宿主刚启动时 `sessionQuery.listSessions()` 可能还是空,原实现拿到空数组就永久放弃,重启恢复静默失效。改为按重试间隔重试,直到列出会话或超出 `freshMs` 窗口。
2. **恢复缺 preset 挂载**。`agents.resume` 不带 preset 时 agent 没有工具与提示变量,恢复后发出的请求无路由。现在按 `header.agentPreset` 走 `agentPresets.resolve` + `mount`。

**重试策略的修正(2026-11-11)**:上面的重试没有区分"服务没就绪"与"近期确实没有会话被写过"。目录扫描本身是权威快照,冷启动、过夜后开机时 `freshMs` 窗口内没有会话是常态,但当时判据要求"列出数 > 0"才算完成,于是每 1s 重扫整棵会话目录直到窗口耗尽——实测 782 会话 44.6ms/次、3000 会话 159.6ms/次,冷启动后 30 分钟内持续占用主线程。

现在按来源区分:`scanStoredSessions` 返回 `source`(`directory` / `partial` / `persistence` / `query`),收工判据由 `scanSettled` 统一给出——只有目录快照完整可读时,空结果才算完成。持久层与全量回退的空列表仍按"可能未就绪"重试;任一子项读取失败(`partial`)也不收工,避免把"读不出来"当成"没有"。这与 D13 一致。

**工位说明**:`scripts/compat/boot-keep.mjs` 默认每轮清 `home/sessions`,跨重启验证要加 `--keep-sessions`。加该参数后已实测通过:

```
列出 4 个存储会话
会话 session-8b1e4f46 事件 37 判定 resume:interrupted
已恢复 session-8b1e4f46
...
```

echo 端 26 个请求里 22 个携带重启恢复文案,证明确实重新发起了 LLM 请求。

**第三个缺陷(端到端才暴露)**:扫描里直接访问 `ctx.workspaceRegistry` 抛 `cannot get property "workspaceRegistry" without inject`,整轮扫描中断,上层 catch 后按重试间隔重试,永远走不到判定。改成 `ctx.get('workspaceRegistry')` 并加 try/catch 兜底。最初的兜底按空集处理(fail-open),后来发现会误恢复已归档会话,已改为拿不到权威集合就不恢复(见下文「归档集合的方向性」)。

### 设置面板

宿主 0.2.2-rc.1 已移除 `settings.register`,`describe()/update()` 才是现役接口,表单来自插件 cordis Config 的 volatile 字段。实测:

- `GET /api/keep-working/config` 返回 `{ok:true, value, defaults}`
- `POST` 写入 `graceMs: 6000` 后回读为 6000,并触发运行期重建
- 客户端半区在 `plugins.bundle.config` 注册配置卡片(key 为包名),与 context 等插件同形态,不占设置导航;`inject: ['slots']` 缺失时宿主报 `cannot get property "slots" without inject`,已补

### 扫描吞吐

首版逐条 `observeSession` 解码全量事件,生产 3615 个会话要跑半小时。两级削减:

1. **先筛后读**。宿主的 `persistence.list()` 要为每个会话解析快照,3615 个耗时 8.6 秒。改为直接扫 `$DSH_HOME/sessions` 目录取 id 与 mtime(1918 个文件 210ms),只对命中者调 `persistence.stat()` 取头部。`持久层快照` 与 `目录扫出` 两条日志区分走了哪条路。
2. **只判尾部**。回合正常结束且有可见回复就跳过,不解析整轮 present。

工位实测:

```
扫描开始        10:17:53.064
目录扫出 1 个近期会话   10:17:53.065
按修改时间筛出 1 个候选  10:17:53.072
已恢复           10:17:53.163
```

从扫描开始到恢复完成 **100ms**,两个会话时 316ms。生产同款数据筛出 4 个候选、恢复 3 个共 17.5 秒,其中 8.6 秒是改前的 `persistence.list()` 固定开销。

### 归档集合的方向性

恢复是写操作,误恢复已归档会话会真的发请求消耗额度。生产实测踩到过:冷启动 25 秒时 `workspaceRegistry` 还在异步加载,`archivedSessionIds` 抛 `workspace registry is not started yet`,旧代码 catch 后当空集处理,导致 3 个恢复里有 2 个是已归档会话。

现在改为拿不到权威集合就本轮不恢复、下一轮重试(`result.complete = false`),方向与只读场景的 fail-open 相反。
