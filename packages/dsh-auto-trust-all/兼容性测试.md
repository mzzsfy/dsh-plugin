# dsh-auto-trust-all 兼容性测试

包定位:web 监听 0.0.0.0(经 bundle patch 翻转官方 webserver 行 host 默认值),并包装 webServer 全部路由把每个实际到达请求的 Host 头实时注册进 `webRuntime.trustedHosts` 与 `connection.trustedHosts` 双数组,防伪造 Host 与泛域名入口被信任闸门拒绝;认证层(原生 cookie 与 startup-auth 会话)原样保留。无 UI,断言全走 HTTP。

| 层 | 内容 | 手段 |

### L2 判据

- 仓库根 `node scripts/smoke-load.mjs`:本包必有输出行 `OK   @mzzsfy/dsh-auto-trust-all`(全仓判据 0 FAIL);`--profile` 变体测安装副本同判据。
- 隔离环境 boot:bundles 裁剪为四项——`dshmarket`(市场插件,提供 L3 探针端点 `/dsh-market/installed`)+ `@deepseek-ai/dsh-base`(宿主基座)+ `@deepseek-ai/dsh-web-app`(web 面,提供 `webStartup` 服务,本包 patch 表达式 `ctx.webStartup.host/port` 依赖它)+ `@mzzsfy/dsh-auto-trust-all`。裁剪操作:用 node 脚本读改隔离 profile 的 package.json(`JSON.parse` → 替换 `dsh.profile.bundles` 数组 → 写回无 BOM;禁止 pwsh 字符串手术改 JSON,有静默截断事故史),改完回读核对条目数;`DSH_HOME` 指向隔离 home,端口 9191,启动须 `dsh web --no-open --port 9191`(`--port` 必需,缺省落 3080)。判据:无 pending 条目、无插件装载错误、console 出现 `auto-trust-all: 动态信任已启用 (bind 0.0.0.0, 容量 100), 既有信任 N 项: ...` 横幅。

## L3 功能面断言

约定:探针端口 9191(隔离环境固定);`<T>` = boot 启动 token,取法:在 boot 日志中 grep `token=`,取 `token=` 之后的值(官方日志会把 URL 的 `http://` 截成 `ttp://`,只影响按整行复制 URL,grep `token=` 不受影响);伪造 Host 探针必须用 curl.exe(`-H "Host: ..."`),Node fetch 与浏览器把 Host 列为 forbidden header 不可显式设置,用它们会产生假阴性。探针域名无需 DNS 解析,Host 头纯文本即可。

## L4 共存层(全家桶共启交叉)

- 全家桶(全部 @mzzsfy 包 + `dshmarket` / `@deepseek-ai/dsh-base` / `@deepseek-ai/dsh-web-app` 三基座)共启:本包 activation live、findings 0,#3 探针仍 200;console 无插件报错。
- 与 dsh-web-startup-auth 完全共存:两者都会遮蔽 webServer 注册方法,委托链任意激活顺序保持正确(L1 场景 6a/6b 锁定)。实测判定:未认证 index 请求先完成 Host 登记(registered 行出现,纯观察先行),随后被会话/认证层拒绝(401 认证文本或 303 回跳,非数据);认证后探针 200。本包不提供任何 cordis 服务,零服务冲突。
- 与 dream-skin 等同构自守卫插件:它们实时读同一 `webRuntime.trustedHosts`,本包注册对其同步生效;该数组无独立 HTTP 观测面,双写正确性由 L1 场景 22-24 覆盖。
- 日志噪声交叉注意:多样化 Host 流量下 registered/evicted 日志逐条输出,全家桶日志审计时属预期行为,勿误判为异常;可作为入口审计手段使用。

## 专项注意

- **本包无 UI,全部断言走 HTTP,不需要 playwright**;判定「信任生效」以 #4 的 registered 日志为硬判据(伪造探针的 HTTP 200 打在无 Host 检查的 market 读端点上,不构成信任证明);68 字节认证文本(401 `dsh web authentication required; ...`)是 index 认证失败形态,只应出现在打 `/` 的请求上。
- **探针工具**:Node fetch 与浏览器禁改 Host 头(forbidden header),必须用 curl.exe(`-H "Host: ..."`);浏览器探针自带 `sec-fetch-site` 头,受官方闸门 cross-site 拒绝影响,与 curl 探针形态不同,勿混用判定。curl 不发 `sec-fetch-site`,不受该拒绝影响。
- **拦截层全景(读磁盘官方与市场插件源码静态定案:dsh-client-connection / dsh-host-webserver / dsh-host-frontend-static / dshmarket@1.47.0,跨版本以首轮实测校准)**:webserver 纯路由分发,无任何检查。connection 服务的 Host/Origin 闸门只作用于其 channel 路由(`/api` 类 prefix):Host 可信(本包注册先于闸门执行,首个请求即过)+ `sec-fetch-site` 非 cross-site + Origin 可选(存在时须 `new URL(origin).host` 与 Host 头 WHATWG 归一化 host **含端口**全等);**Referer 无任何层检查**;闸门失败 403 "forbidden",过闸未认证 401 "unauthorized"。index 页面(`/` 与 dist index)走 authorizeIndex:cookie(按 Host authority 绑定)或 `?token=`(GET `/` 铸币 303),失败 401 + 68 字节认证文本。其余插件自有路由按注册方自定:dshmarket 的 `/dsh-market/installed` 为 GET 读端点,无 sameOrigin、无 cookie 检查(变更类 POST 才查 `new URL(origin).host === Host` 原串),故本表伪造探针打它恒 200,装/未装本包无差;本包生效的判据是 registered/evicted 日志,fence 侧正确性由 L1 场景 22-24 覆盖。
- **token 与探针的关系**:token 机制仅服务 index 页面认证(`?token=` 只在 GET `/` 上生效,铸按 Host authority 绑定的 cookie 后 303 回 `/`),与 Origin/Referer 无关——不存在「带来源头即可免 token」的检查(早期实测「服务端 API 必须带 Origin/Referer」经源码核对为误归因:真实变量是 cookie 与端点自身检查)。本表全部探针(#3-#15)默认无需 token/cookie,唯一用 token 的是 #10 的 LAN 页面 URL。若首轮实测 API 探针返回 401(端点认证行为随 market/宿主版本变化),按铸 cookie 序列校准:`curl.exe -s -c jar.txt "http://127.0.0.1:9191/?token=<T>"` 后加 `-b jar.txt` 重试,并把实测结论回填对应断言项。
- **LAN 地址探针(#10)依赖 boot 日志实际输出**(10.x.x.x 形态 token URL),多网卡/虚拟网卡环境下以日志为准,勿假设固定 IP;`Get-NetTCPConnection` 找不到 9191 监听时先确认旧进程已杀净——端口被占时新进程启动报错退出,探针若仍通是打到了未杀净的旧进程,会得出「改了没生效」的假结论。
- **淘汰语义**:淘汰域名重访即自愈——注册记账无黑名单,重访与首注册同一路径重新登记并恢复信任(#13),evicted 行是容量审计信号而非拉黑标记;默认容量 100,长时间多域名测试留意挤占。两层语义勿混淆:L1 mock 层与真实链路的重访自愈走同一注册路径(场景 16);外部直接收缩信任数组时,已记账条目重访不自动回填(命中记账即短路),属既定行为非缺陷。
- **冷启动语义**:延迟激活、等待行、横幅等启动时序判定必须冷启动验证,HMR 热重载掩盖竞态。
