# dsh-tunnel 兼容性测试

包定位:宿主进程内反向代理。path 模式 `/p/<name>/` 前缀 strip 转发(保留 Host,附 `x-forwarded-host/for/proto`,3xx 同源根绝对路径 `Location` 单头补前缀,WS 任意路径);subdomain 模式摘取 `webServer.server` 的 request/upgrade 监听,Host 首标签命中即全路径全协议透传,未命中原样委托。向 ai 注册 `tunnel_open/list/close` 三工具(可开关注销),看板经公共 WS 总线 `@mzzsfy/dsh-tunnel`;持久化 `~/.dsh/dsh-tunnel/tunnels.json`(随 `DSH_HOME`),重启恢复。

分层定义见 [DEVELOPMENT/dsh-api-alignment.md](../../DEVELOPMENT/dsh-api-alignment.md) 条款 3;维度定义与判定口径见[兼容性检查总纲](../../docs/兼容性测试/兼容性检查总纲.md)。

## 维度检查点(在既有功能格之外)

### 双入口与转发正确性(D03/D05/D12)

1. path 模式:目标应用收到 `x-forwarded-host/for/proto`,Host 仍为入口 Host;3xx 的 `Location` 只对同源根绝对路径补 `/p/<name>` 前缀,绝对外域 URL 不改写。
2. subdomain 模式:隧道域名下 `/api/*` 与宿主 upgrade 路由**不**命中;未命中的 Host 原样委托宿主监听,宿主 GUI 不受影响。
3. path 模式不做全协议透传:仅 HTTP 前缀 strip + WS strip;需要根路径的应用必须走 subdomain。
4. 名称规则:纯数字拒绝(与纯 IP 首段冲突);占用入口域名首标签(如 `dsh.example.com` 用 `dsh`)拒绝或提示。

### 故障边界(D09/D11)

5. 目标端口无人监听 → 502,错误信息可读。
6. 目标接受连接但不回头 → `connectTimeoutMs` 后 504;头到即解除,SSE 长响应不被超时杀掉。
7. 目标在 WS 升级后断开 → 隧道侧清理,不残留 upgrade 监听/句柄。
8. `tunnels.json` 损坏或半写 → 启动不崩,按空表处理并告警;合法 JSON 内非法行逐行跳过并告警;不承诺按行恢复/坏行保留,下次 persist 覆盖为空表。

### 恢复与生命周期(D06/D08)

9. 重启前保持一条 path 与一条 subdomain 未 close → 重启后均恢复;面板与 `tunnel_list` 一致。
10. 恢复失败(目标已下线)→ 行保留磁盘、列表 `active:false`;目标恢复后下次激活重试成功。
11. 卸载插件 → 监听层不摘,载体置空后宿主路由原样透传;`tunnel_close` 停对应载体;重启后无残留隧道。

### 安全与配置(D10/D12)

12. 跨源 POST `/api/tunnel/tunnels` → 403;无 Origin 放行;非 JSON content-type → 400。
13. 伪造 Host 直连隔离端口 → 照常受理(仓库安全边界);不得把缺 Host 校验判为缺陷。
14. `aiTools` 关闭 → 新会话工具列表无三件;重开恢复;看板增删不受影响。
15. `connectTimeoutMs` 改动即时生效(无需重启),对已建立连接不追溯。

## 人工执行方式

执行前置(强制):按 [docs/兼容性测试/测试与隔离方法.md](../../docs/兼容性测试/测试与隔离方法.md) 的隔离红线执行,禁止在宿主机生产实例上直接测试——宿主经 compat 自动化装入隔离 pnpm 闭包,独立 `DSH_HOME`(工位统一预置的插件数据目录隔离 env 见 scripts/compat/run.mjs),compat 工位隔离端口(9291 段,多会话并发时在 9291-9310 段手动指定互不相同的 `--port`,勿都落默认);生产 profile、`~/.dsh` 与 3080 零接触。下述步骤中的宿主与端口均指隔离实例。

1. 隔离宿主启动(`node scripts/compat/run.mjs --version <v> --only dsh-tunnel --keep --port <段内自选端口> [--work-root <独立目录,同版本并发必加>]`,或 boot-keep.mjs 驻留形态 `--port <段内自选端口>`),token 取隔离工位 boot.log,不装生产 profile、不起生产 3080
2. 路径模式: ai 调 `tunnel_open`(name/app, targetPort/本地 http 服务端口), 浏览器访问 `http://127.0.0.1:<隔离端口>/p/app/`, 断言目标应用页面透出
3. 子域名模式: ai 调 `tunnel_open`(name/web, targetPort, entry/subdomain), 浏览器访问 `http://web.localhost:<隔离端口>/`, 断言根部署应用页面透出且 WebSocket 应用(如 jupyter)内核通道可用
4. ai 调 `tunnel_list`/`tunnel_close`, 断言列表含 entry/access 与关闭后回落宿主页面
5. 重启隔离宿主, 断言两类隧道均自动恢复(重启前未 close 的条目)
6. 自动化: `node --test "test/*.test.mjs"` 全绿(行为语义) + `node scripts/compat/tunnel-fullchain.mjs` 全链路 PASS(隔离实例九项探针)
7. ai 开关(legacy ≤0.1.6 与 0.1.7+ 各跑一遍): 设置卡关「允许 ai 使用隧道工具」→ 新会话工具列表无 tunnel_open/list/close; 再开 → 工具恢复可用; 期间看板增删照常; 0.1.7+ 另断言设置页自动配置节出现 aiTools/connectTimeoutMs/sidebarTab 三字段且改动即时生效
8. 设置卡双代形态(可选): 0.1.7-rc.1+ 在插件管理页本包详情页配置 section(`plugins.bundle.config`, key=包名)见「隧道」形态切换卡; 0.1.2-0.1.5 在设置>插件页(`settings.plugin.item`)见同卡

## 专项注意

- 端口与目标服务自备:隔离工位内起最小 HTTP/WS 目标服务(或 jupyter),不得探测生产端口。
- 子域模式依赖泛解析;无 DNS 时用 `*.localhost` 仅本机可解析,不能据此判公网形态通过。
- 危险操作:`tunnel_close` 会断开正在使用的目标应用;不要在共享终端/生产页面操作。
- 证据:九探针输出与 L3 截图落 `.compat/<版本>/`;失败行保留证据要同时看面板与 `tunnels.json`。
- 历史文档中的固定端口 18123 属人工流程记录,AI 会话按 AGENTS 自测规约用随机端口与本次实例。
