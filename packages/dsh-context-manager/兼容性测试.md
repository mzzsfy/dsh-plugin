# dsh-context-manager 兼容性测试

包定位:历史输入浮层(Alt+↑ 或输入框工具排按钮唤起,范围导航/搜索/收藏回填)+ 插话撤回(未应用的插话撤回至输入框)+ 对话 fork(重写式分叉/进行中轮分叉/自动重发)+ 标题栏复制 sessionId(悬停显隐)+ 设置页「插件」区「对话增强」启停卡片(六开关)。宿主半区十条 `/api/context/*` 路由(git-clone 与 clone-enabled 两条属克隆仓库功能,克隆链路断言见 clone.test.mjs 与 L2 深测项)与 settings `context` namespace;client 半区经 `conversation.input.dock` 插槽注入三个 dock(历史/撤回/fork,历史 dock 即浮层挂载宿主)、经 `conversation.session.header.actions` 插槽注入标题栏复制按钮;历史按钮不在 dock 内,另行以 MutationObserver 注入官方输入工具排(克隆 `_add` 类名,`data-cx-hist-trigger` 标记),样式注入自带 `data-plugin` 标记;公共通知依赖 dsh-common-tools 可选消费(缺失通知置空),client 对 `remote.session` 等版本脆弱面点分 inject 交 cordis 门控。

## 插话撤回气泡形态基准与失效史(断言 #5 的机制依据)

撤回图标显隐由「气泡 DOM 形态 ↔ inbox 投影行集」对齐驱动,而气泡 DOM 形态完全由宿主 dsh-client-ui-chat 决定且随宿主版本漂移——本功能三连失效全部源于宿主形态变更,验证者须先掌握本节基准再执行断言 #5 与撤回深测。

### 宿主气泡三形态(0.2.1-rc.2 源码锚定:dsh-client-ui-chat ChatFlow.pendingInputs)

宿主每帧把 `inbox['next-step']` 的 user 行(source.kind==='user')与本地 pendingSubmissions 组装为 pendingInputs:投影行带 rpcId 且本地有对应 submission 时**以 submission 替换渲染**,无本地 submission(切会话回来/刷新)渲染投影行本体,剩余本地 submission 排尾;DOM 文档序与该组装序一致。撤回扫描读同一投影的 user 行,故顺序对齐成立:

| 形态 | 出现场景 | DOM 标记 | 撤回匹配路径 |
|------|----------|----------|--------------|
| 双标记 echo | 发送插话的会话内,Host 已落投影(主场景,可撤窗口全程) | `data-pending-steering` + `data-submission-echo` | pending 顺序对齐(文档序 ↔ 投影序) |
| 纯 pending | 切其他会话再切回、刷新页面(本地 submission state 清空) | 仅 `data-pending-steering` | pending 顺序对齐(同上) |
| durable steering | 插话已入转录(刷新后材料化为 node) | `data-chat-flow-kind="steering"` + `data-chat-node-key` | node-key 提取 messageId ↔ 投影行 id |

未应用插话在可撤窗口内不进转录,无 durable 形态;Host 未确认(无投影行)的排尾 echo 由「行存在性检查」天然不注入,无需按标记排除。

### 失效史(为什么本功能反复出问题)

| 轮次 | 症状 | 根因 | 修复与教训 |
|------|------|------|-----------|
| 一(ee1cdeb) | 图标从不出现 | 只扫 durable 选择器,可撤窗口几乎全程处于 pending 阶段 | 补 pending 路径;教训:单测桩只造 durable DOM,172 绿测错了阶段——桩必须锚定宿主真实形态 |
| 二(f4caa82) | 带格式插话无图标,刷新后出现 | pending 按渲染文本匹配,Markdown 渲染致 textContent ≠ 原文 | 改文档序↔投影序顺序对齐,文本退出匹配;教训:「失配降级等 durable」假设不成立,运行中插话被应用后直接进转录,不产生可撤 durable 节点 |
| 三(4bfce5e) | 发送后无图标,切其他会话切回才出现 | 顺序对齐残留「排除 echo」过滤,0.2.1-rc.2 发送会话内主形态即双标记 echo,被整体错杀;切回后变纯 pending 才命中 | 去掉 echo 排除,`[data-pending-steering]` 全集参与对齐;教训:排除条件的原始动机(Host 未确认防误配)已被顺序对齐的行存在性检查覆盖,形态修复后旧防御要重审是否退化为错杀 |

共性回归模式:**宿主 dsh-client-ui-chat 气泡渲染面变更 = 本功能高危回归面**。宿主升级(兼容性窗口主测版本滑动)后必须重验断言 #5,且验证动作必须是「发送插话的会话内立即查图标」——只刷新后查看只会覆盖纯 pending 形态,恰好漏掉主场景(第三轮失效因此逃过上轮隔离工位复验)。

### 验证与误判防范(本功能专项)

- 断言 #5 的「发送后立即」是硬要求:图标须在**发送插话的同一会话内**出现,「切会话回来才出现」即第三轮失效回归,不得判过;
- 环基境受限项(见专项注意)导致隔离环境静态样本造不出真实发送链路,撤回注入的形态覆盖由 L1 client-steer 桩锁死(三形态用例 + 契约断言「不得排除 echo」),L3 只验存在性与即时性;
- 宿主源码核对方法:形态结论过疑时直接读宿主安装目录 `node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-client-ui-chat/lib/client.js` 的 `pendingInputs` / `PendingSubmissionBubble` / `PendingSteeringBubble`,以源码为准,不信任何历史文档(含本文档)。

## 专项注意

- 专项计划存在过期描述(设置分区名/用例数),以其执行深测前先对照本文档回归表与 src 校准。
- 端口:专项计划历史约定 3083;并入整体计划执行时统一 9191,按当轮环境选择,生产端口(3080)不碰。
- fork 重写式语义(分叉边界/轮内插话/open 失败回填)在专项计划标「待复测」:兼容性回归不阻塞其复测,复测安排在深测轮。
- 人工/环境受限项:IME 组合输入需真人输入法参与,自动化无法模拟(实现为 isComposing 首位守卫);真实插话撤回需会话运行中发送插话,隔离环境静态样本不满足——撤回顺序与禁用门控已由单测覆盖,实机项留日常使用确认。
- 误判防范:时序相关断言(开关延迟到达、注入门控、停用生效)必须冷启动验证,不信热重载表现;重启前按命令行杀净旧宿主进程,防请求打到旧进程得出「改了没生效」假结论;boot 日志乱码按 UTF-8 读取;控制台偶发的其他插件报错为环境噪音,断言只针对本包;隔离环境无历史数据时浮层显示空态文案,勿把空态误判为功能失效。
