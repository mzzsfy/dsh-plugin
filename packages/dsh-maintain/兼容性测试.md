# dsh-maintain 兼容性测试

包定位:设置内「版本与运维」页(settings.section 分区,order 45),提供 npm dist-tag 版本检查、追踪通道、更新内容、受管 A/B 宿主升级、升级前检查、进度与安全重启。受管布局(`<prefix>/.dsh-maintain` 下 install-a/install-b + `dsh_link` 目录链接 + 命令入口改写)在首次升级时自建;无法定位受管安装时升级入口返回 `409`「受管安装不可用」。已装版本取链接指向槽的清单版本,与进程启动时缓存的运行版本分别展示。`POST /api/maintain/preflight` 检查布局、权限、磁盘、锁、状态、npm、Node 与目标插件兼容性;硬不兼容仍拒绝。新宿主 `appReady` 后核对运行版本/路径与插件健康;候选 CLI 冒烟不等同于宿主 profile 就绪。

M0 验收边界:受管升级只升宿主。`POST /api/maintain/upgrade` 的 `upgradePlugins: true` 或 `safeMode: true` 在建任务或写盘前直接 `409`,两项开关均从确认弹窗移除。预检、受理、提交前检查、失败收尾与启动复查都不得自动调用 `updateBundle` 或 `setBundleEnabled`。仅既有 `safe-mode.json` 支持显式人工恢复,不属于升级步骤。M1 隔离验证未通过前不开放插件事务;M0 的通过不能作为事务已验收的证据。

host 半区通过 webServer 具名 `/api/maintain/*` 路由供浏览器调用,首行回问宿主闸门(`connection.requestRejection`),写路由另校验 Origin 与 Host 同源及精确 `application/json` content-type。配置在 0.1.7+ 宿主使用静态 `Config` 与 configEditor 原地热更,旧宿主走 settings `maintain` 命名空间;检查结果只存内存。timer、settings/configEditor 为软依赖,缺失或方法面不齐时干净降级。重启直接终止宿主进程,退出码为 `RESTART_EXIT_CODE`(75)。

救援说明验收。安装确认弹窗展示救援命令（默认目标 `rescue`，当前 profile 同名时改用 `dsh-rescue`），并提示同名救援 profile 会被重建。展开说明可查看救援界面的作用范围和文件写入时机。启动、状态查询和弹窗预检期间 `rescue.txt` 保持原样。通过路由测试向隔离 home 提交「开始安装」请求，确认服务端检查通过后、安装编排启动前创建或更新文件。写入失败时仍受理安装并提示用户。

## 测试分层与执行流程

| 层 | 内容 | 手段 |
|---|------|------|
| L1 单元层 | 覆盖纯逻辑、上游拉取、受管布局与编排、预检与能力门控、进度与结果三态、历史与回执、路由集成、重启等待、client 守卫和双实现对拍;平台专属用例按平台跳过。`scripts/acceptance-managed-upgrade.mjs` 是另行运行的真实 npm 隔离冒烟,不验证宿主 profile 就绪 | 包目录 `npm test` |
| L2 装载层 | 全包冒烟加载 + 隔离宿主 boot 干净降级判据 | 仓库根 `node scripts/smoke-load.mjs`(本包在清单内)+ 隔离 profile 启动 |
| L3 功能面层 | 界面断言(面板骨架、版本/通道/设置/重启/弹窗形态)+ 单次经批准的重启;受管安装的真实执行不在兼容性轮次 | 隔离宿主静态与页面断言 |
| L4 共存层 | dsh-common-tools(反馈依赖)、dsh-settings-nav-icons(导航图标)、设置分区排序与全家桶交叉 | 同装验证 + 页面级回归 |

### L2 装载层

- 冒烟覆盖:scripts/smoke-load.mjs 遍历 packages/ 下全部含 package.json 的目录(symlink/junction 一并收),逐个动态 import 各包 main——OK/FAIL 逐行输出,入口缺失打 SKIP,任一包加载失败即 exitCode 1;`--profile` 参数切换为遍历 profile node_modules/@mzzsfy 测安装副本。本包 main 为 src/index.js,在清单内:宿主半区顶层依赖(@deepseek-ai/schemastery 等)缺失或自身命名导出损坏当场暴露。src/client.js 非 main,不被该脚本 import,其装载由本层 boot 判据与 L3 覆盖。
- 隔离环境 boot 判据:本包经 `dsh plugin add @mzzsfy/dsh-maintain --profile <隔离profile>` 注入(完整命令含 --profile 指向隔离 profile,不得对开发宿主所在 profile 执行;bundle patch 在该 profile root 插入 id=maintain 行),重启一次宿主完成首装载;判据 = activation live + diagnostics findings 0 + 无 pending/装载错误 + 页面无 `Failed to load plugins`。顶层 inject 仅声明 webServer:宿主缺 webServer 时 fiber 不激活即干净禁用,不 pending 拖死 boot。
- 软依赖降级日志表(出现以下文案属降级预期,不判失败,但须核对与宿主实际能力一致):

| 日志文案 | 含义 | 面板形态 |
|---|---|---|
| 「timer 服务方法面不可用,自动轮询停用(面板可手动检查更新)」 | timer 缺失或方法面不齐 | 顶部警示「自动轮询未运行(宿主定时服务不可用);可手动点『检查更新』,其余能力不受影响。」,手动刷新不受影响 |
| 「活跃工作检测降级,升级门拒绝/重启门放行(<服务名>): <明细>」 | agents/jobs/terminals 服务面缺失或方法面不齐(按服务键进程内首见一次) | 升级入口照常可点,受理时 409 且正文带「活跃工作检测不可用…降级面: <明细>」;重启照常放行 |
| 「升级锁存在(残留待人工核验,内容含 operationId/pid/startedAt): <路径>」 | `<prefix>/.dsh-maintain/upgrade.lock` 残留(上次安装超时/切换后状态不确定) | 属升级失败文案(last.ok=false)进「升级」卡与浮条;人工核验后手工删除该锁 |
| 「升级锁删除失败(已保留供人工核验): <路径>」 | 锁文件删除失败(权限/占用) | 同上,下次升级继续被残留锁拒绝 |
| 「[dsh-maintain] 升级状态轮询失败: <原因>」 | client 侧升级观察拍失败(宿主重启窗口内) | 首条与之后每 15 条一条,浮条维持「升级进行中」;超上限转「升级状态长时间未更新」 |

- 受管目录与锁:<prefix>/.dsh-maintain 下 install-a/install-b(两个槽)、upgrade.lock、state.json(阶段与 operationId、previousVersion、health)、safe-mode.json(安全模式禁用清单)、candidate-home/npm-cache/npmrc(候选隔离环境)、log/entries.json(命令入口改写备份);`dsh_link` 在 `<prefix>[/lib]/node_modules/@deepseek-ai/dsh/dsh_link`,命令入口为 `<prefix>/dsh{,.cmd,.ps1}`(Windows)或 `<prefix>/bin/dsh`(POSIX)。目录在首次升级时自建,测试前若存在残留 `upgrade.lock` 先核验再删,否则升级会被「升级锁存在」拒绝(本流程不触发安装,只做存量卫生检查)。本包无数据目录,检查结果仅内存,重启即清,测试不留脏数据。

### L3 功能面断言

受管安装的真实执行不在兼容性轮次:「安装」入口按通道目标与升级/重启瞬态禁用;打开弹窗后,预检可进一步禁止「开始安装」。在隔离环境校验弹窗及预检,不提交真实升级或执行网络安装验收;候选验证/切换失败为受理后 `upgrade.last.ok=false`,原语单测不代表宿主 profile 已就绪。

断言于隔离宿主上以 playwright 执行;选择器与文案均对照 src/client.js 校准。沿用既有等待约定:页面加载等 9s、导航点击后等 2s、渲染断言前等 2.5s(页面调宿主版本 API,网络慢时控件延迟到达)。默认态指页面初次进入、无升级历史、无弹窗时的形态。

### M0 副作用门槛（L1 / 隔离替身）

- 分别提交 `upgradePlugins: true` 和 `safeMode: true`（也覆盖 `autoRestart: false`）,断言直接 `409`,不启动预检、任务或安装,不写升级状态或插件资产。
- 把旧扫描能力注入预检,断言状态不提供在线同步升级能力(`upgradePluginsAvailable=false`),预检不提供可执行的安全模式(`okWithSafeMode=false`、`safeMode.available=false`、候选为空)。
- 在预检、宿主单升的成功与失败分支、旧 pending 和旧安全模式记录的启动复查中,用一旦调用即失败的 `updateBundle` / `setBundleEnabled` 替身和清单/锁文件/包树前后对照验证零自动改包。旧记录只有显式恢复时允许调用 `setBundleEnabled`。
- 受理时发现硬不兼容，返回 `409`。准备期间才启用硬不兼容插件时，开启自动重启并验证最终只读复扫阻止切槽和退出。复扫不可用时核对 `plugin-rescan-unavailable` 审计日志、其余门控通过后能切槽、插件资产不变。热重载维护插件后，旧任务仍占用同一安装目录的维护门闩，拒绝再次升级、重启和人工恢复。旧实例在切槽提交前卸载时应中止，已经调度的退出仍只执行一次。
- 同一 prefix 的两个 profile 共用安装槽。只有发起 profile 能提交对应操作的健康与回执。独立进程持锁写入新操作后，旧回执必须在同一把锁内复读并被拒绝。无归属的旧记录只读展示，可在浏览器本地确认已知失败。
- 已禁用插件的兼容错误不导致运行健康失败。只有归属本次启动的健康样本能确认成功。回执按 `operationId` 与结果类别核验，拒绝未知结果和与当前结果不一致的确认。
- 候选 Worker 取到插件选择快照后、安装链接已切换但命令入口尚未提交时，分别用宿主同源锁尝试启用插件。两次写入均受阻，正常释放锁后同一操作可写入。取锁失败时安装链接和命令入口保持原样，且不调度退出。该场景覆盖遵守宿主写锁的操作。
- 路由夹具在取得 profile 写锁后注入 `.plugin-manager/run.json`，分别记录测试进程的存活 PID 和损坏内容。验证两种情况均在读取候选插件清单前失败，命令入口、安装链接和运行记录保持原样，且不调度退出。rc.5 在启动 pnpm 后才发布记录，记录发布前的崩溃窗口不在此用例覆盖范围内。
- 同时注入遗留运行记录和状态写锁争用。验证磁盘状态停在 `ready-to-switch`，不出现待重启记录。路由报告原门控错误及落盘失败，旧宿主继续接收新回合，残留升级锁阻止再次升级和强制重启。候选安装超时、切换后出错和回滚失败另有保护性退出回归。
- 健康检查 GET 在途时受理升级，迟到 GET 不得覆盖受理结果或停止观察。同一操作连续换两个新进程且均报告 `healthChecking` 时，验证页面接收末次启动的终态。刷新场景使用回环服务模拟 B 和 C 的启动快照，实际刷新浏览器，让新页面从 B 的健康检查开始观察。组件用例验证 C 的失败原因可见，浏览器夹具验证 C 成功后发送对应的回执确认。每个页面保持一路顺序请求，后续启动沿用本页开始观察的时限，完成或超时即停止。
- M1 须在隔离夹具中证明候选包树、锁与进程回收边界、就绪和恢复能力;验证未通过前不开放插件事务。普通 boot 和候选 CLI 冒烟不能代替这些证据。

## 专项注意

- 兼容性轮次不执行「受管升级」:允许打开确认弹窗进行预检和查看救援说明,不点击「开始安装」,不运行网络安装型脚本验收——兼容性环境一旦真实安装即整体作废。候选验证链路(npm ls + CLI 冒烟)由包内单测以真实子进程覆盖。
- 其他真实上游交互仍需单独说明:「刷新」会请求registry dist-tags;「更新内容」会请求GitHub Releases;「重启宿主」需隔离宿主且仅允许经明确批准的兼容性轮次触发。
- 环境前提:隔离宿主经 `dsh plugin add @mzzsfy/dsh-maintain --profile <隔离profile>` 注入并重启完成首装载(不得对开发宿主所在 profile 执行);宿主须提供 webServer(顶层 inject,缺失即插件整体不激活);registry 默认 `https://registry.npmjs.org`,隔离环境不可达时按 #8/#9/#17 的兜底分支判,不误报失败。
- 宿主代际差异:timer/settings 经嵌套 inject + 方法面守卫,缺失时面板降级提示照常服务(L2 日志表);重启不需要启动器具备额外能力(直接终止进程并以 `RESTART_EXIT_CODE`=75 离场,托管默认策略据此拉起),任何宿主代际下按钮均可用;配置面双形态特性检测(照 dsh-llm-pi-gateway,不做版本硬编码):宿主 settings 有 register/update 方法面即 legacy 命名空间形态(0.1.2–0.1.6),否则走 0.1.7 形态——静态 `Config` 导出(根级 volatile 包装)+ `configEditor.edit(fiber.entry)` 写回 + loader volatile 原地热更;0.1.7 宿主 configEditor 缺失时写路由 500(「configEditor 服务不可用」)。降级是合法形态,不算失败;但「干净禁用」底线不变——任何代际下不得加载崩溃、不得 pending 拖死 boot。
- 误判防范:
  - 控件数延迟:页面调宿主 `/api/maintain/status`,网络慢时控件数延迟到达,断言前等 2.5s;
  - 徽章/通道 option 随上游 dist-tags 与运行版本实时浮动:「有新版本 x」的 x 为通道目标版本,option 文本带「  (版本号)」后缀——断言按形态正则或 includes 通道名,不锁字面值;「上次检查」时间自然走动,不锁具体值;
  - 升级卡默认不渲染(仅当升级进行中或存在历史时出现):「升级」卡缺席是预期,不是功能缺失;运维入口以「重启」卡为准;
  - 加载态 `.dm-head__hint`「正在读取版本与宿主状态…」为瞬态(模块加载即预取状态),错误态标题「状态读取失败」+`.dm-note--error` 内「读取状态失败:<原因>」仅在 status 接口故障时出现——均不作稳定断言;持续「状态读取失败」先查宿主日志再判,不得带病跑断言;
  - 「版本与运维」文本同时出现在设置导航项与本页标题两处,断言 #3 选择器必须锚定导航容器(叶子节点匹配),防命中页内标题造成假阳性。
- 断言保留记录:原 5 项全部保留融入,无一删除——原 1→新 1、原 2→新 2、原 3→新 3、原 4→新 4、原 5→新 14。仅新 14 措辞按现源码修正:检查/升级入口的按钮现文案为「刷新」「安装」(原「检查/升级」字样仍存于「检查中…」「上次检查」「升级」卡题等副本文案),预期由「(含检查或升级)且含重启」收紧为「含刷新、安装、重启宿主」;其余按源码补全了选择器、placeholder 与预期文本。另:面板警示文案存在源码残留——pollRunning=false 通知原文为「自动轮询未运行(宿主定时服务不可用);可手动点『检查更新』,其余能力不受影响。」,其中「检查更新」为源码残留(实际按钮名为「刷新」),断言该通知时按源码原文匹配,不按按钮名纠正。
- 安装入口可点只表示通道目标就绪且当前未升级/重启;不能取代预检与服务端受理门,也不能证明安装或健康检查成功。

## 维度检查点(补充)

1. **托管矩阵（另行批准的隔离宿主升版专项）**:至少覆盖一种真实托管形态下的「检查 → 候选验证 → 切换 → 重启」。进入安装激活前的确定性失败应保留原链接和命令入口，旧宿主继续运行。安装或验证超时、切换状态不确定，或已进入激活后失败结果无法落盘时，按保锁和保护性退出判据验收。
2. **门控 fail-closed**:门控面不可用时拒绝升级;有活跃 agent/job 时拒绝且不可越过;重启的 force 语义单独验证。
3. **锁**:验证超时/切换后状态不确定时保锁并强退;人工核验后可解锁;并发第二请求被拒。
4. **外部源**:GitHub 页面抓取上限与缓存只存成功结果;Release 缺失给出可读提示与源站链接;npm registry 不可达不影响已装版本展示。
5. **路由与退出语义**:13 条路由都必须在业务面前回问宿主闸门(401/403),写路由另拒跨源;重启/升级落定的退出码为 75(非零),托管默认策略(systemd `Restart=on-failure`、supervisord `autorestart=unexpected`)据此拉起——这两条按固定行为验证,不得写成「已启用但未测」。

## 判据补充

分别记录常规兼容轮次（不安装）、M0 替身门控验收和另行批准的隔离宿主升版专项。实际切槽、重启后装载或长时运行的子项缺证据时,仅该子项记 P 并写原因;已覆盖的 API 拒绝、并发门控与结果状态单独记录,不得用按钮可点、普通 boot 或退出码代替真实升版证据。必测子项未通过时不得宣称完整兼容。
