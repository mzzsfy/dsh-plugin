# dsh-maintain 升级根治规格审核报告

> 历史文档(2026-11-10 注):审核对象 [升级根治-BDD.md](升级根治-BDD.md) 已被 [透明升级-设计.md](透明升级-设计.md) 取代并实施;本文"不通过"结论仅针对被替换的规格。

## 结论

**不通过；当前规格不能证明根治，不应据此进入实施。**

审核目标为 [升级根治-BDD](./升级根治-BDD.md)，不审核或撤销工作区其他会话的代码改动。
本轮按“安装时无人使用正在改写的树；失败和未知状态不得开放启动；通过验证才能交付”三个安全条件审查。
先前“已能根治”“面板入口混装树进不了运行态”的结论撤回。

下列问题不是通过写入“已知局限”即可满足的例外：其中多数正是用户要求消除的事故路径。

## 阻断项

### R-1：超时即开放启动，未知写入状态会重新变成活体安装

定位：[INV-4](./升级根治-BDD.md#L61-L63)、[S-8](./升级根治-BDD.md#L250-L252)、[L-2](./升级根治-BDD.md#L309-L310)。

反例：编排器启动 npm 后被杀，npm 或其子孙仍在写；gate 到期被循环视为不存在，宿主开始加载同一棵树。即使 npm 已退出，半装树也不能凭时间证明完整。

**deadline 只能证明等待时间已到，不能证明所有写者已退出或树已经健康。**

修正要求：deadline 到期转“恢复待核验/人工介入”，不能作为 spawn 授权。恢复者必须先确认没有写入者，再验证或修复树，成功后显式开放启动。

### R-2：回滚失败后两小时自动开放，原 crash loop 明确可复现

定位：[受控停机窗口](./升级根治-BDD.md#L123)、[L-3/L-4](./升级根治-BDD.md#L311-L315)、[已知局限章节](./升级根治-BDD.md#L381)。

反例：新装、重装、回滚皆失败，树已损坏；两小时后重新启动循环，按 L-4 恢复 spawn。若宿主启动即崩，maintain 的 apply 和红牌根本没有运行机会。

修正要求：`failed-rollback` 或树健康状态未知时持续禁止自动启动；只能由外部修复并重新验证，或者显式人工操作解除。不把永久失去服务与安全停机混为一谈：可提供恢复命令，但不能拿带伤启动作自动自愈。

### R-3：lock 检查再覆写不是原子互斥

定位：[lock 接管](./升级根治-BDD.md#L84-L91)、[S-7](./升级根治-BDD.md#L248-L249)。

反例：两个编排器同时读取 `role=host` 的锁；两者皆被允许接管，各自覆写自己的 PID，然后各跑一次 npm。PID 存活检测和 role 字段不能阻止该时序。

修正要求：对实际安装资源使用原子互斥；启动意图与编排器所有权交接绑定同一 operationId。释放必须校验持有者身份；不得在未知状态下删别人的锁。

### R-4：WMI 调用超时被当成“确定没有创建进程”

定位：[WMI 失败判定](./升级根治-BDD.md#L68-L71)、[W-2](./升级根治-BDD.md#L259-L265)。

反例：WMI Create 已创建编排器，PowerShell 调用在返回结果前超时。宿主按照 W-2 删除全部保护信号并继续服务，编排器却可能已经运行；下一次升级也可获准进入。

修正要求：区分确定失败与结果未知。通过 operationId、编排器 ready/ack 与可核验的进程身份完成交接；结果未知保留启动屏障，查询确认后才清理。原子发布状态文件，避免另一进程读到截断状态后放行。

### R-5：等固定宽限不等于已确认宿主或 npm 树停止

定位：[编排器序列](./升级根治-BDD.md#L194-L198)、[S-2b/S-5](./升级根治-BDD.md#L239-L246)。

反例：taskkill 被拒绝或只终止一部分进程；宽限结束后进入下一步 install。同一资源存在旧 npm 写者与新 npm 写者，或仍运行的宿主。

历史实现 `src/upgrade.mjs`(3197fdd 删除)曾承认 `stillRunning` 这种失败形态。因此规格不能用“等待宽限”替代“确认退出”。

修正要求：杀进程后验证退出结果；不能证明没有写者时保持屏障，进入显式异常终态，不重装、不回滚、不拉起。

### R-6：资源是 npm 安装树，gate 却按 DSH_HOME 隔离

定位：[单 hostPid](./升级根治-BDD.md#L171-L175)、[gate/status](./升级根治-BDD.md#L92-L100)。

反例：同一全局 dsh 树被两个 DSH_HOME、两个端口或两个 profile 使用。A 的循环查 A 的 gate，B 的循环查 B 的 gate；升级仅等待 A 的 PID 退出，B 仍运行并可继续重拉。

修正要求：互斥与启动许可统一绑定规范化的实际 npm prefix/安装树，不按 HOME 声称机器唯一。升级前停稳全部受管消费者；消费者不在管理协议内时拒绝自动升级，不能默默降级仍称根治。npm 实际 prefix 也须核对，不能仅从 node.exe 所在目录猜测。

### R-7：verifyTree 定位规则与真实 Node/npm 解析不符

定位：[INV-1](./升级根治-BDD.md#L40-L46)、[T-3](./升级根治-BDD.md#L220-L221)。

已做只读验证：发行版 `0.2.0-rc.2` 的 web-app 声明 connection；web-app 自己的 `node_modules/@deepseek-ai/dsh-client-connection/package.json` 不存在，但从 web-app 建立 `createRequire` 可以正常解析到 dsh 根下的 `node_modules/@deepseek-ai/dsh-client-connection/package.json`。

```text
reference: @deepseek-ai/dsh-client-connection/package.json
directChildExists: false
Node resolution: <dsh>/node_modules/@deepseek-ai/dsh-client-connection/package.json
```

这正是 npm 的同层提升与 Node 的祖先目录查找，不是损坏。按规格仅检查引用方的直接子目录，当前树会被判坏。

修正要求：按引用方上下文使用真实 Node 模块解析语义，再读取解析到的 package metadata；遍历以实际包身份/realpath 去重，处理循环引用及 optional peer 等语义。不得用插件仓库的 peer range 代替宿主发行闭包的事实证据。

### R-8：版本一致不足以证明文件一致，boot 失败也没有回滚闭环

定位：[只检查版本/不冒烟](./升级根治-BDD.md#L40-L53)、[ok 后退出](./升级根治-BDD.md#L199-L205)、[循环启动](./升级根治-BDD.md#L377)、[内容截断局限](./升级根治-BDD.md#L395-L396)。

反例：所有 package metadata 已是目标版本，但一个 JS 文件仍是旧内容或已截断。verifyTree 返回通过，编排器写 ok、退出，循环开始 boot 并崩溃；规格没有把 boot 失败回传到编排器的边，也没有自动回滚动作。

“失败分类没有消费者”不能推出“不需要冒烟”。冒烟的消费者是交付决策，而不是故障分类。

修正要求：增加独立于生产宿主的交付前验证：至少关键入口与隔离 profile 启动/就绪测试；如声称字节完整性，需要依据安装来源建立文件清单/摘要对比。tarball 的整体 integrity 与本地文件逐项摘要是不同概念，不能用“没有公开逐文件哈希”直接推出验证不可做。更稳妥的候选为预装到独立候选树、验证通过后切换受管入口，保留旧完整树；不能在本报告中把尚未验证的候选当成已完成方案。

### R-9：修复按钮仍在活体内安装，第二入口没有根治

定位：[修复路径](./升级根治-BDD.md#L28-L29)、[W-5](./升级根治-BDD.md#L274-L280)。

修复仍调用宿主内 npm，保留了导致事故的原机制。红牌只能提高可见性，不降低此路径的并发替换风险。手动 npm 导致宿主起不来时红牌甚至不可达。

修正要求：升级与修复都走宿主外事务，修复仅豁免“当前树健康”检查，不豁免停机与交付前验证。不要保留一个被称为“修复”的活体安装旁路。

### R-10：path.resolve 不能消除 nvm junction 别名

定位：[INV-7](./升级根治-BDD.md#L77-L82)、[W-3](./升级根治-BDD.md#L266-L268)。

只读实测：

```text
process.execPath: C:\nvm4w\nodejs\node.exe
guessed manifest: C:\nvm4w\nodejs\node_modules\@deepseek-ai\dsh\package.json
known installed manifest: <nvm 实体版本目录>\node_modules\@deepseek-ai\dsh\package.json
path.resolve equality: false
fs.realpath equality: true
```

使用 path.resolve 字符串全等会误拒绝指向同一物理树的合法路径。

修正要求：核实实际 prefix，并按 realpath/物理身份判定同一资源，同时定义大小写与符号链接处理。另：上轮审查关于 `path.join` 必定保留 `..` 的说法不成立，Node 的 join 本来就会归一这些段；真正缺失的是 junction/符号链接归一。

## 补充：两条同样阻断根治的启动竞态

### R-11：损坏持久信号被当成无信号，实际是 fail-open

定位：[信号格式与损坏读取](./升级根治-BDD.md#L92-L100)、[循环的解析回退](./升级根治-BDD.md#L365-L375)。

gate 写入中途被读到半个 JSON，循环把解析错误变成 deadline=0，直接启动；status 写入失败则回退 `none 0`，忽略 failed-rollback。规格没有原子替换、写失败的终态、事务身份或带持有者检查的清理约束。所谓 fail-closed 实际放行。

修正要求：原子发布、严格校验、按 owner 条件释放；已有事务的记录损坏或读取结果未知时保持阻断，显式输出恢复诊断。终态耐久提交失败时不能删启动屏障。

### R-12：检查 gate 与执行 spawn 之间没有原子启动许可

定位：[循环片段](./升级根治-BDD.md#L363-L377)。

反例：循环检查 gate 不存在后被调度暂停；升级方发布 gate 并开始停机交接；循环恢复后直接 `dsh web`，没有再与升级方协调。即使使用正确的 gate 内容，也未实现读取 gate 与注册新宿主之间的互斥。

修正要求：启动与升级必须在同一个原子资源协议下登记；否则不能证明“安装窗口无新消费者”。单纯追加检查会缩小竞态窗口，但不消除它。

## 其他问题

- [弹窗契约](./升级根治-BDD.md#L160-L164)保留一个只影响文案、无法改变重启动作的 `autoRestart` 选项，用户选择与实际行为不一致。直接删除失效开关与字段，显示“本次操作必停机”。
- [POSIX 范围](./升级根治-BDD.md#L15-L19)继续保留活体升级。可以明示“仅 Windows 根治”，不能把双平台产品整体称为根治；不支持的平台应禁用自动升级或提供等价离线事务。
- [手写 range 子集](./升级根治-BDD.md#L139-L147)引入额外错误面。优先调查成熟 semver 实现及构建打包方式，使外部 worker 带上独立依赖快照；“单文件”不等于必须手写满足性规则。
- WMI `\"` 的跨 shell/PowerShell/Windows argv 引号规则未被本轮实际创建进程验证，不再接受前轮“技术正确”的无测试结论。实施时应使用避免多层字符串解释的传参方式，并在隔离环境覆盖含空格/单引号/非 ASCII 的路径。

## 六维度结论

| 维度 | 结论 |
|------|------|
| 内部一致性 | 不通过：自动重开放行与未验证树不交付冲突 |
| 完整性 | 不通过：孤儿写者、未知 spawn、kill 失败、boot 失败回传缺失 |
| 歧义性 | 不通过：锁交接、prefix 资源身份、失效开关语义不明 |
| 外部一致性 | 不通过：真实 Node 解析与 nvm 路径别名证伪关键规则 |
| 结构合规 | 章节齐全，但不是可靠性证明 |
| 可执行性 | 不通过：按文字实现会误判健康树，且重新打开原事故路径 |

## 本轮处置与后续边界

本轮仅做审核：修改规格首页状态为“未通过”，将未解决阻断落档，不擅自把它改写为另一套升级架构。不修改已有实现、生产配置、启动循环或宿主进程。
下一步是重新设计阻断项对应的事务/启动协议，再审查；在这些阻断清零以前不得宣称根治，也不得凭“又审了几轮”替代隔离故障注入验证。
