# 性能基准

改性能前先有基线：`scripts/perf/bench.mjs` 提供可复现的微基准，测量各包热路径的单次调用成本。没有基线数据的"变快了"不算证据，也不接受。

## 用法

```bash
node scripts/perf/bench.mjs                     # 跑全部用例,人读表格
node scripts/perf/bench.mjs --only usage         # 只跑名字含该片段的用例
node scripts/perf/bench.mjs --json .work/perf-base.json    # 落基线
node scripts/perf/bench.mjs --compare .work/perf-base.json # 比对,不可判定或劣化即非零退出
```

`--json` 是**合并写入**:文件中本次没跑的用例保留旧条目,只覆盖本次跑到的;不稳的测量不写入,避免污染基线。

`--compare` 与 `--only` 一起用会因"基线里有但本次没跑"而非零退出,这是刻意的:局部重测不能声称整体没有回归。需要局部比对时另建只含该子集的基线文件。

用例可用 `samples` 覆盖进程内默认的 5 轮取样(与跨进程重复次数无关,成本敏感时调小,离散度要求更严时调大)。

`--worker <name>` 是子进程入口,由主进程内部调用,不需要手工使用。

## 测量约定

- **每个用例在独立子进程里测量，重复 5 次取中位数。** 同进程内先后跑不同用例会让 JIT 与堆状态互相污染：实测同一用例单独跑与在全套内跑差 40%。
- **单轮时长按时间预算定，不按固定迭代数。** 工具先试跑校准，把单轮拉到约 2ms；预热累计 500ms 才取样。固定预热 1 轮在本机实测造成 1.2–2.2 倍偏差。
- **统计量归一为"每次调用"。** 用例若在单次 `run` 内批量调用被测函数（如逐任务投影 1000 次），用 `callsPerIteration` 声明批大小，否则不同用例的中位数不可比。
- **离散度 = 5 个进程结果的最大/最小。** 超过 1.4 标 `(不稳)`，该用例不下结论。

## 噪声底与判据

**这套工具在本机的噪声底约为 10%–20%，`--compare` 只能发现 40% 以上的劣化。** 依据：同一份代码重复测量，跨进程极差实测最高 1.46；与固定基线比对合计 25 次，其中 4 次给出错误的「劣化」判定。

所以：

- 回归阈值 1.4、改善阈值 0.6，两侧对称：都要越过噪声底才判定。阈值低于噪声底会把抖动当结论。
- **小于 40% 的变化不要用这套工具判定**。需要这类精度时用同进程交替 A/B（两版实现轮流跑、取比值中位数），靠共模抵消环境噪声。
- 离散度反复超阈值的用例标 `judgeable: false`，只打印数字，不参与判定。`bug-perf/passthrough-782` 是典型：单次调用的绝对量级落在本机计时噪声里，跨进程极差实测可达 2.97x，测不出可信差异。判据是实测离散，不是绝对耗时。
- `--compare` 的失败语义是严格的：缺基线、用例名不匹配（改名）、环境或输入规模不符、任何一项"不作数"，都非零退出。跳过不等于通过。
- 基线必须字段完整（`medianMs`、`spread` 为有限数）才参与比对，坏条目单列而不静默通过。

## 新增用例

在 `scripts/perf/cases/` 加文件，导出 `cases` 数组，每项为 `{ name, description, scale, callsPerIteration, judgeable, samples, setup, run }`（`samples`、`judgeable`、`callsPerIteration` 可省略）。`name` 用 `<包短名>/<场景>` 形式，是比对基线的键，改名等于丢弃历史数据。

用例不写盘、不出网；时间锚点用 `Date.UTC` 构造（本地时间会随机器时区改变输入）；随机输入用 `seededRandom` 固定种子。

**时区限制**:`usage-dash` 的桶键(`dayKey`/`hourKey`/`minuteKey`)用本地时区取值,UTC 锚点只固定输入时刻,不固定桶串。基线的 `__meta` 记录 `tz`,与当前时区不符时比对直接判为环境不符并非零退出;跨机器共享基线前先核对该项。

**旧基线的校验缺口**:没有 `__meta` 字段的基线(手工编写或早期版本生成)会跳过环境与规模校验,直接进入比对。无法确认来源的基线应当重跑生成,不要复用。

## 判据

单次调用成本要结合触发频率判断，不是绝对值越小越好：

- 落在用户交互路径上（打开面板、翻页、发送消息）的单次成本超过 50ms 才构成可感知卡顿。
- 周期任务看"单次成本 × 频率"占单核的比例，超过 1% 才值得改。
- 一次性启动成本单独看，不并入稳态指标。

测量到的热点与处置结论记在任务记录里，不写进本文件；本文件只管怎么测。
